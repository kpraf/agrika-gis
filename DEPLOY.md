# Deploying AgriKA-GIS (free tier)

This deploys three pieces:

| Piece | Where | Notes |
|-------|-------|-------|
| Database (Postgres + PostGIS) | **Supabase** (free) | PostGIS built in; doesn't auto-expire like Render's free DB |
| Flask API | **Render** Web Service (free) | Spins down after ~15 min idle → first request is slow (~30–60s) |
| React frontend | **Render** Static Site (free) | No spin-down |

You can host the DB on Render instead, but its *free* Postgres is deleted after a fixed
window — bad for something you need live at defense. Supabase is the safer free choice.

---

## 1. Database — Supabase

1. Create a project at supabase.com. Save the database password.
2. **Schema + PostGIS + seed in one shot**: open the Supabase **SQL Editor**,
   paste the entire contents of **`backend/db/supabase_setup.sql`**, and Run.
   That file enables PostGIS and creates every table + the base seed (roles,
   municipalities, seasons) — no separate extension toggle needed.
3. Get the connection string: Dashboard → **Connect → Session pooler → URI**.
   Use the **Session pooler**, NOT the direct connection:
   - Direct (`db.<ref>.supabase.co:5432`) is **IPv6-only**; Render's free tier
     egresses over IPv4, so it will time out.
   - The **Session pooler** is IPv4 and session-mode (prepared statements work,
     so psycopg3 needs no extra config). Avoid the *transaction* pooler (`:6543`).

   It looks like (note the dotted `postgres.<project-ref>` username):
   ```
   postgresql://postgres.xxxxxxxx:YOUR-PASSWORD@aws-0-<region>.pooler.supabase.com:5432/postgres
   ```
   If connections fail, append `?sslmode=require`. This same URL works for both
   the local seeding below and Render's `DATABASE_URL`.

### Load boundaries + yield data into Supabase
The tables already exist (step 2 above). Now load the geometry + yield data from
your machine. From `backend/` with the venv active:

```bash
# point every script at Supabase for this shell (PowerShell: $env:DATABASE_URL = "...")
export DATABASE_URL="postgresql://postgres.xxxx:YOUR-PASSWORD@aws-0-<region>.pooler.supabase.com:5432/postgres"

# 1. import boundaries (30 municipalities, 682 barangays), then the real yield data
python scripts/import_boundaries.py
python scripts/load_municipality_yield.py --csv db/ricelytics_laguna_yield.csv

# 2. create the 3 portal accounts on prod (interactive — set real passwords)
python scripts/create_user.py
```

> On Windows PowerShell use `$env:DATABASE_URL = "..."` instead of `export`.

## 2. Deploy on Render (Blueprint)

The repo has a `render.yaml`. In Render: **New + → Blueprint → pick this repo**. It
creates two services: `agrika-gis-api` and `agrika-gis-web`.

### API service env vars (set in the Render dashboard)
| Key | Value |
|-----|-------|
| `DATABASE_URL` | the Supabase URI from step 1 (the app rewrites the scheme for psycopg automatically) |
| `JWT_SECRET_KEY` | auto-generated by Render — leave it. **Must exist:** the API refuses to start without it (there is no built-in default) |
| `CORS_ORIGINS` | the frontend URL, e.g. `https://agrika-gis-web.onrender.com` (no trailing slash) |

### Frontend service env var
| Key | Value |
|-----|-------|
| `VITE_API_URL` | the API URL + `/api`, e.g. `https://agrika-gis-api.onrender.com/api` |
| `VITE_CARTO_API_KEY` | CARTO Basemaps key — removes the "API key required" watermark on the map tiles |

### Ordering (because the two URLs reference each other)
1. Deploy the **API** first. Copy its URL.
2. Set the frontend's `VITE_API_URL` to `<api-url>/api` and deploy the frontend.
3. Set the API's `CORS_ORIGINS` to the frontend URL and redeploy the API.

`VITE_API_URL` is read at **build time**, so changing it requires a rebuild of the
frontend.

---

## 3. Verify
- `https://<api>/api/health` → `{"status":"ok"}`
- Open the frontend, log in, confirm the map/monitoring/analytics/reports load data.
- If the map is empty or login fails with a network error, it's almost always
  `CORS_ORIGINS` (must match the frontend origin exactly) or `VITE_API_URL`.

## 4. Scheduled data pipeline (GitHub Actions)

`.github/workflows/data-pipeline.yml` runs the data pipeline every **Monday at 02:00
Philippine time** and on demand (**Actions → Data pipeline → Run workflow**). Each run
fetches the current month plus the previous one (Open-Meteo weather, Sentinel-1 /
Sentinel-2 statistics from Copernicus) for the 30 municipalities and for every barangay
with a reported yield, upserts them into the production database, checks them, predicts
the latest season once its six months are complete, and adds one row to the
`pipeline_runs` table.

Add three **repository secrets** (GitHub → Settings → Secrets and variables → Actions):

| Secret | Value |
|--------|-------|
| `CDSE_CLIENT_ID` | Copernicus Data Space OAuth client id (same as in `backend/.env`) |
| `CDSE_CLIENT_SECRET` | its client secret |
| `PIPELINE_DATABASE_URL` | the Supabase connection string (same value as Render's `DATABASE_URL`) |

**First run (brings Supabase up to date, uses no Copernicus units):** Actions → Data
pipeline → Run workflow, with **from_month** `2025-12` and **skip_fetch** ticked. It
loads the data files already in the repository, verifies them, and stores the Dry 2026
forecasts. After that the Monday schedule needs nothing from you.

- **Copernicus quota.** The free tier allows 30,000 processing units a month. One month
  of data costs 274 for the 30 municipalities and 13 for the 42 barangays, so a normal
  run (two months) costs about 575 and a month of weekly runs about 2,500. A run stops
  fetching at 3,000 units (`--max-pu`), and what it spent is stored in
  `pipeline_runs.processing_units`.
- **See the runs:** `python backend/scripts/pipeline_runs_report.py` (add `--prod` for
  Supabase), or the job summary of each run on GitHub.
- GitHub pauses scheduled workflows after 60 days without a commit to the repository;
  it emails first, and one click re-enables them.
- Yield records are not part of the schedule: PhilRice and the City Agriculture Offices
  publish no API, so yields still come in through the Import page.

## Notes / gotchas
- **Never commit secrets.** `backend/.env`, real passwords, and `seed_accounts.py`
  stay out of git (already gitignored). Set everything via Render env vars.
- **Cold starts:** the free API sleeps when idle; warn your panel the first hit is slow.
- **PostGIS must be enabled** on the DB before `import_boundaries.py` runs.
- **App DB role:** locally the app uses the `postgres` superuser; on Supabase the
  provided `postgres` user is fine. If you later lock this down, the app only needs
  read/write on its tables + usage of PostGIS functions.
